===============================================================================
 HUELLITAS DE AMOR - QUE HACE LA WEB (ESTRUCTURA)
 Sistema de gestion veterinaria
 https://huellitasdeamorvet.vercel.app
===============================================================================

En una linea: pagina publica de la clinica + tres paneles privados (cliente,
veterinario, administrador), con API en Express y base de datos PostgreSQL en
Supabase. Quien puede hacer que lo decide un catalogo de permisos guardado en la
propia base de datos.

REPORTES EN PDF  (/api/reportes/pdf/...)
  Se generan con pdfkit y se devuelven como stream, sin escribir en disco:
  en una funcion serverless no hay donde dejar el archivo.

  /historia/:id           historia clinica completa con linea de tiempo
  /vacunacion/:id         certificado de vacunacion con lote y firma
  /receta/:id             formula medica veterinaria

  /hospitalizacion/:id    informe de internamiento con epicrisis

   - Un cliente solo saca documentos de SUS mascotas.

     de la clinica lo imprime el PDF sale marcado como PRELIMINAR.

  Cada descarga queda en archivos.reportes_generados: la historia clinica es
  un documento medico y hay que poder decir quien la saco y cuando.

 2. RECORRIDOS PRINCIPALES
===============================================================================

AGENDAR UNA CITA
  Cliente elige servicio -> elige veterinario -> elige fecha
  -> el servidor calcula los huecos libres descontando citas y bloqueos
  -> el cliente confirma -> queda "programada"
  -> el veterinario la ve en su agenda -> la atiende y registra la consulta
  -> la cita pasa a "atendida" y queda en la historia clinica de la mascota

  Cuatro reglas, aplicadas EN EL SERVIDOR (no solo en pantalla):
    1. No se reservan horarios ya ocupados
    2. No se reservan fechas pasadas (y hoy exige anticipacion minima)
    3. No se agenda fuera del horario del veterinario ni de la clinica
    4. Un veterinario no puede tener dos citas a la misma hora
       (disponibilidad + SELECT FOR UPDATE + indice unico en la base)

ATENDER Y COBRAR
  Consulta registrada -> se factura el servicio y los productos usados
  -> facturar un producto lo DESCUENTA del inventario en la misma transaccion
  -> se registran pagos -> un disparador recalcula saldo y estado
     (pendiente / parcial / pagada)
  -> anular la factura devuelve el producto al inventario

MOVER INVENTARIO
  El stock nunca se escribe a mano: todo pasa por movimientos_inventario y lo
  ajusta un disparador de la base, asi que kardex y existencias no pueden
  contradecirse. Un "ajuste" fija el total que queda, no una diferencia.

 3. QUIEN VE QUE (PERMISOS)
===============================================================================

Las rutas no preguntan "eres admin?" sino "tienes este permiso?".
Los permisos son filas en la base con codigo modulo.accion
(citas.crear, historia.ver_todas, auditoria.ver, inventario.gestionar...).

  ROL           PERMISOS   ALCANCE
  cliente          35      Sus mascotas, sus citas, su historia, sus facturas,
                           sus recetas, tienda, plan, puntos, PQRS, el plan
                           preventivo de su mascota, la lista de espera y las
                           lecturas de su propio dispositivo
  veterinario     122      Todo lo clinico y su agenda: urgencias,
                           hospitalizacion, farmacia, laboratorio, imagenes,
                           nutricion, telemedicina, las once especialidades
                           (odontologia, cardiologia, dermatologia,
                           oftalmologia, rehabilitacion, dolor, anestesia,
                           comportamiento, genetica, reproduccion,
                           neonatologia), bancos de sangre y tejidos,
                           prevencion, cronicos, calidad e interconsulta.
                           Nada de seguridad, facturacion, contratos,
                           finanzas ni configuracion
  admin           199      Todo, salvo lo que solo tiene sentido para cliente

  El catalogo pasa de 54 a 214 permisos. Quitarle una capacidad a un rol sigue
  siendo un DELETE en rol_permisos.

Quitarle una capacidad a un rol es un DELETE en rol_permisos: la ruta empieza a
responder 403 y la opcion desaparece del menu, sin tocar codigo.
Crear un rol nuevo (recepcion, auxiliar) es insertar el rol y elegirle permisos.

Ademas del permiso se comprueba la PROPIEDAD: un cliente con citas.ver_propias
solo ve las suyas; la clinica, con citas.ver_todas, las ve todas.

 5. SEGURIDAD
===============================================================================

  - Contrasenas con bcrypt (10 rondas). Nunca se devuelve el hash.
  - JWT firmado; en produccion obligatorio y de 32+ caracteres.
  - Sesiones CON ESTADO en la base: del token solo se guarda el hash SHA-256.
    Cerrar sesion, cambiar contrasena o bloquear la cuenta invalidan el token
    de inmediato, aunque al JWT le queden horas de vida.
  - Bloqueo por intentos: 5 fallos seguidos con el mismo correo -> 15 minutos
    de espera para esa cuenta (frena la fuerza bruta aunque cambien de IP).
  - Accesos y auditoria: quien entro, quien cambio que, con el antes y el
    despues en JSON y la IP.
  - Recuperacion de contrasena: token de un solo uso, 30 minutos de vida;
    al usarlo se cierran todas las sesiones de esa cuenta.
  - El usuario y sus permisos se recargan de la base en CADA peticion.
  - El registro publico solo crea clientes.
  - Consultas parametrizadas siempre. Validacion con zod en cuerpo,
    parametros y query.
  - Rate limiting: 10 logins / 15 min, 20 citas / hora, 300 peticiones / 15 min.
  - Helmet con CSP y CORS con lista de origenes permitidos.
  - Subida de archivos: solo JPG/PNG/WebP, 3 MB, nombre generado por el
    servidor, guardado en Supabase Storage.
  - RLS activado en todas las tablas y sin politicas: la clave anon de Supabase
    no puede leer ni escribir nada. Todo pasa por la API de Express.
  - Login con mensaje y tiempo de respuesta uniformes: no revela que correos
    existen.

===============================================================================
 7. COMO SE LEVANTA Y SE PUBLICA
===============================================================================

  npm install
  npm run configurar      asistente del .env
  npm run db:setup        carga schema.sql + seed.sql en Supabase
  npm start               http://localhost:3000   (npm run dev = recarga auto)
  npm test                pruebas unitarias, sin base de datos
  npm run lint            revisa el codigo
  npm run deploy          publica en Vercel (NO toca la base de datos)
  npm run deploy -- --recargar-base   borra y recrea la base (cuidado)

  Vercel sirve frontend/ como sitio estatico y la API de Express como funcion
  serverless en /api/*, todo bajo el mismo dominio.
  Comprobacion rapida: https://<dominio>/api/salud
